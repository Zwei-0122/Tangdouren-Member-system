# 给店主的一页说明：会员系统上线

会员功能（糖豆人会员）的代码已经写好并在测试库验证过了。线上环境只需要做**一件事**：执行一次数据库迁移。

---

## 你要做的

**1.** 登录你们的 Supabase 项目，左侧菜单点 **SQL Editor**，再点 **New query**

**2.** 打开仓库里的 `docs/上线迁移-一次执行.sql`，把**全部内容**复制粘贴到那个编辑框里

**3.** 按 **Run**（快捷键 `Cmd+Enter`）

会弹一个提醒框，写着 `Potential issue detected / destructive operations`。这是正常的，先点 **Run query** 继续。
（它删的是两样东西：旧的 5 参数版结算函数、以及两张新表上刚建的约束。都是「先删再建」的写法，不会碰任何现有数据。）

**4.** 看到绿色的 `Success. No rows returned` 就完成了

整个过程不到一分钟。这个脚本**可以重复执行**，万一中途出错，改完再跑一次不会出问题。

---

## 这个迁移做了什么

| 动作 | 内容 |
| --- | --- |
| 建 1 张表 | `members`（会员身份：邮箱、姓名、加入时间、同意来源） |
| 给 1 张表加 2 列 | `timer_sessions` 加 `member_id`（这单属于哪位会员）和 `reward_eligible`（这单是否计入奖励进度） |
| 建 2 张表 | `member_rewards`（解锁出来的奖励）、`member_benefits`（VIP 月卡的生效记录） |
| 建 1 个视图 | `member_visit_days`（按伦敦自然日算到店次数，同一天来多次只算一次） |
| 建 6 个函数 | 结算时算会员折扣与核销奖励、撤销结算、VIP 激活、把订单挂到会员名下等 |
| 升级 1 个函数 | `settle_timer_session` 从 5 个参数扩到 8 个，**老调用方式照旧可用**，不影响现有的计时结算 |

**不删表、不删数据。** 脚本里那句 `DROP FUNCTION` 只删旧的结算函数签名（要被新版本替换），`DROP CONSTRAINT` 只删刚落的两张新表上的约束，`DROP TABLE` 只出现在注释里（回滚说明）。

---

## 迁移之前 vs 之后

| 阶段 | 表现 |
| --- | --- |
| 迁移前 | 会员页面能打开，但提交时提示「查询失败，请重试」。**计时、预约、结算、优惠券全部照常**，不受影响 |
| 迁移后 | 会员功能完整可用：注册、到店计数、奖励解锁、VIP、结算折扣 |

所以这个迁移不存在「必须停机」的问题，找店里不忙的时候跑就行。

## 想复验（可选）

仓库里有一份验收脚本 `docs/verify_via_api.py`，覆盖 64 项规则（VIP 日期边界、£2 券核销与撤销回退、朋友券用在他人的订单上、刚解锁的奖励不能当次用等等）。

在**有该项目 service key 的机器上**，把它放在仓库根目录跑：

```bash
python3 verify_via_api.py
```

应输出 `通过 64/64`。这个脚本会读写几笔测试数据，跑完会留下两位测试会员（`demo.a@` / `demo.b@tangdouren.test`），可以手工删掉。

## 三条规则（2026-09-16 已确认）

| 情况 | 规则 |
| --- | --- |
| VIP 生效期间能不能用别的优惠 | **默认按 VIP 的 85 折结算**。顾客如果想用手里那张券或奖励，店员在结算面板点「改用其他优惠」，选中的券或奖励替代 VIP 折扣（当次放弃 VIP，剩余天数不顺延）。什么都不选时系统会拦住，不允许 VIP 会员按原价结账 |
| VIP 期间到店算不算奖励进度 | **算**。VIP 那 30 天里的到店照常累积进度，攒到第 10 次一样解锁下一张 VIP 月卡（同一时间只有一张生效，第二张要等这一张到期后再手动激活） |
| 后台把订单挂到会员名下 | **已结算的订单也能补挂**，但只记「这一单是他来的」：不退折扣、不补发奖励、不动已收金额。已经属于别的会员的订单不能改归属 |
