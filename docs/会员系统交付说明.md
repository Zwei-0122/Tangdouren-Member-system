# Tangdouren Club 会员系统 交付说明

这份文档说明会员系统在哪些文件里实现、跟 PRD v1 有哪些差异、验证到什么程度、还有什么没做。

---

## 一、怎么跑起来

**1. 环境变量**（不进仓库，自己建 `.env.local`）

```
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=
NEXT_PUBLIC_APP_URL=
```

**2. 执行迁移**（必须，否则会员功能不可用）

把 `supabase/migrations/016_members.sql`、`017_member_settlement.sql` 按顺序发到数据库执行一次。
怕顺序搞错就直接用 **`docs/上线迁移-一次执行.sql`**（两个文件已按顺序合并成一份，粘一次、按一次 Run 即可）。

测试库 `rlakqwmedlgpcdasvads` 已经执行过，并在真实数据上通过了 52 项校验。**线上站点的数据库不在开发侧**，
所以这一步由店主侧（或上游 `KeMiaoDaDi` 的技术负责人）在他们的 Supabase 项目里执行一次，开发侧不需要也不应拿到线上库凭据。
顺序不能反，`017` 依赖 `016` 建的表和列。执行方式二选一：

- Supabase 控制台的 SQL Editor：粘贴全文，点 Run，看到 `Success. No rows returned` 即可。
- 或走 Management API：`docs/run_migrations.py`（需要 Personal Access Token，存到 `~/.hermes/secrets/supabase_pat`）。

两个文件都写得可以重复执行（`IF NOT EXISTS`、先 `DROP CONSTRAINT` 再加），手抖点两次不会坏。

**3. 本地起服务**

```bash
npm install
npm run dev -- -p 3002
```

注意用 `http://localhost:3002` 访问，不要用 `127.0.0.1`。Next.js 16 把不同 host 视作跨源，会拦掉 dev 资源，页面看似正常但完全不 hydrate，所有点击都没反应。

**4. 验证**

```bash
node --experimental-strip-types --test tests/member.test.ts   # 32 项
npx tsc --noEmit
npm run build
```

数据库层验收：`docs/verify_member_system.sql`，26 项检查，覆盖 VIP 日期边界、刚解锁的奖励能不能当次用、撤销结算后奖励回退、朋友券用在他人的订单上等。整个脚本在一个事务里跑，末尾 `ROLLBACK`，不会留测试数据。

## 二、迁移做了什么

| 迁移 | 内容 |
| --- | --- |
| `016_members.sql` | 建 `members` 表（邮箱唯一身份、3 条约束、3 个索引、开 RLS）；给 `timer_sessions` 加 `member_id` 与 `reward_eligible` 两列（含 CHECK）；给 `bookings` 加 `idx_bookings_email_key` |
| `017_member_settlement.sql` | 建 `member_rewards`（5 条 CHECK、4 个索引）、`member_benefits`（2 条 CHECK、1 个索引）；建 `member_visit_days` 视图；建 6 个函数：`member_vip_active`、`ensure_member_rewards`、`settle_timer_session`（5 参数版换成 8 参数版）、`unsettle_timer_session`、`link_timer_session_to_member`、`activate_member_vip` |

`timer_sessions.reward_eligible` 是一次结算那一刻固化下来的判断（该单是否有会员归属、且结算时没有生效中的 VIP Month），不是事后推算的。因为 VIP 从激活时刻起暂停进度，事后重算会把激活当天算错。

**迁移未执行前，应用照常工作**。这是刻意设计的：新代码在解析不出会员时不写 `member_id` 列；结算只在真的用会员折扣时才向 RPC 传新参数。所以计时、预约、优惠券、原有结算全都不受影响，只是会员功能不生效。

## 四、与 PRD v1 的差异与口径解释

| # | PRD 说法 | 实际做法与理由 |
| --- | --- | --- |
| 1 | 19.2 结算时固化进度资格 | 认同并采纳，新增 `reward_eligible` 列，结算那一刻写死 |
| 2 | 8 解锁奖励不能用于当次消费 | 折扣按结算前快照计算，奖励解锁放在结算成功之后；挑奖励时排除本单解锁的那张 |
| 3 | 10.4 Friend Reward 转赠 | 复用现有 Coupon Generator 出一张普通 10% 券，`member_rewards.coupon_id` 指过去，关联后这张奖励不能再直接使用。没有新开发 Gift Code |
| 4 | 未提 `bookings.member_id` | **不采纳**。预约页注册不改变计时归属，后台按 `email_key` 反查即可，加列是多余的猜测 |
| 5 | 11.6 多张 VIP Month | 可累计多张未激活，同一时间最多一张生效，到期不自动续，需要手动激活下一张 |
| 6 | 18 撤销结算 | 未使用的可撤销回退；奖励已被后续消费用掉则拒绝撤销并提示，交管理员判断 |
| 7 | 后台禁操作 | 后台不能手动加减到店次数、不能直接改进度、不能补发奖励、不能改邮箱、不能删历史。金额只在结算面板由服务端计算 |

**两处替 PRD 补的解释，需要店主确认**：

1. **Link to Member 只允许挂尚未结算的订单**。PRD 5.2 没说时点。选严格版本的理由是进度必须来自真实结算记录，允许事后改归属等于绕过台账改数字，正是 PRD 第 25 节要防的事。代价是店员遇到已结算的订单要多点两下：先撤销结算、挂上、再结算。
2. **VIP Month 生效期间，普通优惠券也一并禁用**，一律走 85 折。PRD 11.4 的清单只点名了会员奖励。要放开只改 `settle_timer_session` 里 `vip_active AND v_source <> 'vip_month'` 这一处判断。

**执行迁移时发现并修掉的一个真实 bug**（值得记下来，因为它只有真跑才会暴露）：

`ensure_member_rewards` 给会员铸内部券时券码用 `MB` 开头，却没有显式写 `code_prefix`。`015_coupon_prefix.sql` 给该列设了默认值 `TD`，并且有一条约束要求 `left(code, length(code_prefix)) = code_prefix`，于是插入被数据库拒绝（违反 `coupons_code_prefix_check`）。这类问题在列名层面的静态检查里发现不了，必须真调用一次。修法是在插入语句里显式带上 `code_prefix = 'MB'`，顺带带来一个好处：会员内部券在活动报表（`coupon_prefix_usage`）里与店员手工发的 `TD` 券分开统计。
